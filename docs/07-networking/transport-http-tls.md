# Transport, HTTP, and TLS

[← Module overview](index.md) · [Master competency map](../master-competency-map.md)

Last reviewed: **2026-10-10**

## TCP reasoning

TCP supplies an ordered byte stream with connection state, acknowledgements,
retransmission, flow control, and congestion control. It does not preserve
application message boundaries or guarantee that the application processed a
request.

| Symptom | First interpretations to test |
| --- | --- |
| Connect timeout | route/policy drop, unavailable target, exhausted state, or lost return path |
| Connection refused | destination reachable but no listener, reject policy, or wrong endpoint |
| Reset | endpoint or intermediary actively terminated state |
| Slow established flow | loss/retransmission, congestion, receiver pressure, application delay, or MTU issue |
| Intermittent failure | one address/zone/target/path, state exhaustion, or race/timeout mismatch |

Ephemeral ports and connection-tracking tables are finite. Connection reuse,
pool sizing, keepalive, idle timeouts, TIME_WAIT behavior, and retry rate affect
capacity as much as link bandwidth.

## UDP reasoning

UDP provides datagrams without connection, delivery, ordering, or congestion
guarantees. Applications must decide retry, deduplication, ordering, size, and
fallback behavior. DNS commonly uses UDP but can require TCP for large or
truncated responses; blocking TCP/53 creates subtle failures.

## HTTP semantics

Separate transport success from HTTP behavior. Record method, host, path,
status, latency phase, redirect, cache, proxy, and request ID.

- `2xx` indicates protocol-level success, not necessarily business correctness.
- `3xx` can create loops, downgrade risk, or unexpected client behavior.
- `4xx` may originate at CDN, WAF, gateway, proxy, identity layer, or service.
- `5xx` can be generated by an intermediary when no backend response exists.

Retries are safe only when operation semantics, idempotency, timeout budget,
backoff, and retry ownership are understood. Layered retries can amplify load.

## TLS handshake model

TLS establishes protocol parameters, authenticates identities with certificates,
derives keys, and protects later traffic. Diagnose:

1. client and server supported versions/ciphers;
2. SNI and selected virtual host/certificate;
3. certificate name, validity period, chain, and trust store;
4. revocation or policy requirements;
5. mutual-TLS client identity where used;
6. termination point and encryption on every following hop.

A valid certificate for the wrong name is still an identity failure. Disabling
verification converts a diagnosable trust problem into a security incident.

## Timeouts as architecture

Connect, TLS, request, response, idle, keepalive, and upstream timeouts have
different meanings. Work from the customer deadline inward; leave time for
bounded recovery and prevent a downstream layer from running longer than its
caller's useful budget.

## HTTP/2, HTTP/3, and operational differences

Multiplexing reduces connection overhead but can concentrate impact on fewer
connections. HTTP/3 uses QUIC over UDP, so policy, observability, fallback, and
middlebox behavior differ from TCP-based HTTP. Confirm the negotiated protocol
rather than assuming the configured preference was used.
