# Active-Recall Flashcards

[← Rapid-fire revision](rapid-fire.md) · [Next: References and videos →](references.md)

Cover the answer column and retrieve the answer aloud.

| # | Prompt | Answer |
| ---: | --- | --- |
| 1 | Migration outcome | Measurable business or risk change, not cloud adoption itself |
| 2 | Transition architecture | The controlled coexistence of current and target states |
| 3 | Discovery confidence | Source, freshness, validation, and uncertainty attached to an inventory fact |
| 4 | Dependency group | Workloads or components whose safe movement must be coordinated |
| 5 | Rehost | Move with minimal application change |
| 6 | Relocate | Move a compatible virtualized environment with minimal workload change |
| 7 | Replatform | Make bounded platform changes without fundamental redesign |
| 8 | Refactor | Materially change architecture or code for new qualities |
| 9 | Repurchase | Replace capability with another product, commonly SaaS |
| 10 | Retire | Remove a proven-unused or superseded capability safely |
| 11 | Retain | Keep in place with rationale, support, integration, owner, and review date |
| 12 | Landing-zone readiness | Evidence that a real workload can be delivered, controlled, operated, and recovered |
| 13 | Learning wave | Representative, valuable, recoverable production movement used to improve the system |
| 14 | Migration factory | Repeatable flow, roles, artifacts, automation, and feedback across waves |
| 15 | Wave entry gate | Evidence that ownership, scope, dependencies, target, funding, and prerequisites are ready |
| 16 | Authoritative write path | The sole approved source of truth for writes during a transition phase |
| 17 | Fencing | Mechanism preventing conflicting authorities or stale actors from writing |
| 18 | CDC | Capture and apply committed source changes after a baseline copy |
| 19 | Last safe rollback point | Latest time coherent rollback remains within accepted loss and recovery limits |
| 20 | Reconciliation | Comparing source, target, and outcomes using technical and business invariants |
| 21 | Go/no-go authority | Named accountable role empowered to proceed, hold, or abort |
| 22 | Operational acceptance | Owned evidence for support, observability, security, change, recovery, and cost |
| 23 | Hypercare exit | Measurable stability, defect, reconciliation, security, and ownership conditions |
| 24 | Control objective | Required risk outcome that may use different current and target mechanisms |
| 25 | Exception lifecycle | Scope, risk owner, compensating control, evidence, expiry, and removal |
| 26 | Modernization trigger | Evidence that a constraint and expected benefit justify change |
| 27 | Strangler approach | Incrementally replace bounded behavior while routing safely between old and new |
| 28 | Unit economics | Cost normalized by a meaningful business or technical unit |
| 29 | Stranded cost | Legacy cost remaining after workload movement |
| 30 | Full closure | Business, technical, operational, control, legacy, financial, and benefit completion |
