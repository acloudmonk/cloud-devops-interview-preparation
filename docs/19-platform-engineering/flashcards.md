# Active-Recall Flashcards

[← Rapid-fire revision](rapid-fire.md) · [Next: References and videos →](references.md)

Cover the answer column and explain each concept aloud.

| # | Prompt | Answer |
| ---: | --- | --- |
| 1 | Platform decision loop | Customer journey, friction, capability, interface, control, feedback, outcome |
| 2 | IDP versus portal | IDP is the whole delivery platform; portal is one interface |
| 3 | Thin viable platform | Smallest end-to-end capability that solves a measured journey |
| 4 | Platform-as-product | Discovery, roadmap, ownership, support, lifecycle, outcomes, feedback |
| 5 | Golden path | Supported opinionated route for a common workload with guardrails |
| 6 | Product-team boundary | Team retains application, data, SLO, testing, rollout, and on-call ownership |
| 7 | Platform layers | Experience, product/catalog, orchestration, control, resources, evidence |
| 8 | Platform API contract | Versioned schema, behavior, errors, guarantees, limits, owner, lifecycle |
| 9 | Desired-state flow | Request, authorize, validate, plan, reconcile, verify, observe, update, delete |
| 10 | Controller identity | Short-lived, resource-scoped, partitioned from people and workloads |
| 11 | State ownership rule | One authoritative reconciler per field/resource contract |
| 12 | Start right | New workload receives safe defaults, ownership, delivery, telemetry, evidence |
| 13 | Stay right | Continuous version, policy, dependency, drift, and ownership maintenance |
| 14 | Interface set | Portal, CLI, API, Git, IDE over common domain contracts |
| 15 | Supply-chain boundary | Untrusted source/build separated from signing and production authority |
| 16 | Artifact promotion | Move one verified immutable artifact rather than rebuild |
| 17 | Guardrail types | Prevent unacceptable state; detect/remediate broader posture; govern exceptions |
| 18 | Escape hatch | Owned, controlled, time-bound deviation with support and re-entry plan |
| 19 | Platform SLI | User-journey success, latency, reconciliation age, or freshness |
| 20 | Control-plane degradation | Preserve workloads and essential operations when interface/control services fail |
| 21 | Version migration | Inventory, compatibility, canary, overlapping support, tooling, deadline |
| 22 | Adoption evidence | Repeat successful use plus better flow, quality, reliability, and experience |
| 23 | Failure demand | Rework/support caused by failed or confusing platform journeys |
| 24 | Platform economics | Total lifecycle cost versus duplication, wait, incidents, audit, and time-to-value |
| 25 | Multi-cloud principle | Standardize valuable contracts; expose and accept native differences |
